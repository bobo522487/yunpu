# 特性规格：云谱 V1（Cloud Genealogy V1）



---

## 1. 概述

**云谱**是给修谱主事人与修谱工作室用的在线谱牒编纂 SaaS。

**Organization 是租户**：一份工作室可以同时管多份谱。**Project 是一份谱的数据边界**：人物、关系、谱系、谱文、谱书和资料都落在这份谱里，默认不与另一份谱共用人物。

**一句话技术栈**：一个 Bun 进程同时提供 Hono API 与前端静态页；浏览器里是 Vite + React 单页应用；数据在 PostgreSQL 18，访问经由 Drizzle；认证用 Better Auth；文件在私有对象存储。

**领域核心区分**（本文最重要的一条语义）：

> **关系是事实，位置是编者的安排。** 两边互不改写。

---

## 2. 用户场景与验收（User Scenarios & Testing）

### US-001（P1）录入人物与多种姓名

**作为**修谱主事人，**我希望**为一个已故或在世人物录入姓名、字、号、谱名、乳名、谥号，**以便**同一人物在不同史料中的不同称谓都能留存。

**为什么是 P1**：人物是谱牒的原子单位。没有人物，其他一切功能都无法测试。

**独立测试**：新建一个人物 → 录入三个不同类型的姓名 → 刷新页面 → 三个姓名都在，且只有一个被标记为主显示名。

**验收场景**：

1. **Given** 一个已创建的项目，**When** 录入一个带姓氏和名字的人物，**Then** 人物创建成功并显示主显示名
2. **Given** 一个已有主显示名的人物，**When** 再录入一个同类型姓名，**Then** 系统接受（多姓名合法），主显示名保持不变
3. **Given** 一个姓名类型为「谱名」的人物，**When** 录入，**Then** 该姓名字段在界面上有独立的展示位置
4. **Given** 一个姓名类型为「乳名」的人物，**When** 录入，**Then** 该姓名不参与正式称谓排序
5. **Given** 人物已存在，**When** 把主显示名切换到另一个已录姓名，**Then** 切换成功且原主显示名降为普通姓名

---

### US-002（P1）用固定关系类型记录亲属关系

**作为**修谱主事人，**我希望**用父母、收养、继亲、寄养、承嗣、监护、配偶、伴侣这几类固定关系记录亲属，**以便**家庭结构能被可靠地推导出来。

**为什么是 P1**：关系类型是**封闭集合**，这是整个模型能做严格约束的前提。如果允许任意关系类型，所有下游不变量（祖先环检测、兄弟姐妹归组）都会退化为启发式。

**独立测试**：在一个项目里录入父母、配偶各一条 → 查询该人物的家庭视图 → 父母出现在正确的父/母位置，配偶出现在配偶位置。

**验收场景**：

1. **Given** 一个项目，**When** 录入一条 `parent` 关系，**Then** 关系被接受并出现在家庭视图
2. **Given** 一个项目，**When** 录入一条 `spouse` 关系，**Then** 关系被接受且不产生任何 `parent` 关系
3. **Given** 一个项目，**When** 试图录入一种不在封闭集合内的关系类型，**Then** 请求被拒绝，错误明确指出该类型不在允许列表
4. **Given** 一条已存在的 `spouse` 关系，**When** 把两端对调后再记一次，**Then** 写入被拒绝（两端不可互换重复）
5. **Given** 一条 `parent` 关系，**When** 检查被连接的孩子，**Then** 该孩子必须已存在于同一项目中，否则写入被拒绝

---

### US-003（P1）家庭视图由关系拼出，不虚构

**作为**修谱主事人，**我希望**家庭视图（父母、兄弟姐妹、子女、世次）完全由已记录的关系推导，**以便**视图里的每个人都是有据可查的，而不是系统编出来的。

**为什么是 P1**：这是「事实与推导分离」原则的落地。若系统为了填满视图而虚构另一方，数据就不可信了。

**独立测试**：只记录单方父母 → 查看家庭视图 → 缺失的一侧显示为「未知」，而不是自动补一个人。

**验收场景**：

1. **Given** 一条 `parent` 关系只连接了孩子和母亲，**When** 打开家庭视图，**Then** 父亲位置显示为未知，不自动创建人物
2. **Given** 一条 `spouse` 关系，**When** 推导家庭视图，**Then** 配偶双方**不会**被自动写成孩子的父母
3. **Given** 同一对父母有多个孩子，**When** 推导兄弟姐妹，**Then** 这些孩子互相出现在对方的兄弟姐妹列表中
4. **Given** 一个没有父母记录的人物，**When** 推导世次，**Then** 该人物被标记为世次起点，其后代世次逐级递增
5. **Given** 关系事实被修改，**When** 重新推导家庭视图，**Then** 视图随之改变，且视图数据本身不被存储

---

### US-004（P2）在谱系中安排编纂位置

**作为**修谱主事人，**我希望**在某条谱系里安排人物的编纂位置（节点与路径），**以便**表达「这一支排在第几世、第几支」这类编排决策。

**为什么是 P2**：位置是**投影**，不是事实。它是谱牒区别于普通家谱树的关键能力，但排在人物与关系之后。

**独立测试**：创建一个谱系 → 把已有的人物放到该谱系的某个位置 → 查询路径 → 路径与放入的位置一致。

**验收场景**：

1. **Given** 一个谱系与一批人物，**When** 安排一个人物到某位置，**Then** 位置被接受，谱系路径包含该位置
2. **Given** 一个已安排位置的人物，**When** 修改其人物关系，**Then** **位置不变**（关系是事实，位置是安排）
3. **Given** 一个节点，**When** 删除该节点，**Then** **人物不被删除**（删位置不等于删人）
4. **Given** 一个谱系，**When** 查看根节点，**Then** 根节点唯一且符合 `lineage_root` 视图定义
5. **Given** 一个项目，**When** 人物关系形成祖先环，**Then** 关系写入被拒绝，且该写入不产生任何位置投影

---

### US-005（P2）挂载来源引用

**作为**修谱主事人，**我希望**为人物、姓名、关系和事件挂上来源引用，**以便**每条录入的结论都能回溯到史料出处。

**为什么是 P2**：溯源是谱牒产品的核心价值之一，但不影响数据模型的可行性——先做会推迟价值交付。

**独立测试**：为一个事件挂一条来源引用 → 查询该事件 → 显示来源名称与引用位置。

**验收场景**：

1. **Given** 一个事件，**When** 挂一条引用，**Then** 引用被接受并与该事件关联
2. **Given** 一个来源，**When** 查询引用它的事件，**Then** 反向引用列表完整
3. **Given** 一条引用，**When** 引用定位指向一个不存在的人物，**Then** 写入被拒绝
4. **Given** 一个来源，**When** 删除该来源，**Then** 其引用按声明的删除语义处理（不留下悬空引用）

---

### US-006（P2）撰写单篇谱文

**作为**修谱主事人，**我希望**写单篇谱文（富文本、分页、可挂媒体），**以便**记录序言、凡例、修谱说明等文字。

**为什么是 P2**：谱文是内容型功能，与前面的结构型功能（人、关系、位置）正交。

**独立测试**：新建一篇谱文 → 编辑正文并分页 → 保存 → 刷新后内容一致。

**验收场景**：

1. **Given** 一个项目，**When** 创建一篇谱文，**Then** 谱文创建成功且有标题与正文
2. **Given** 一篇谱文，**When** 两个会话同时编辑，**Then** 后提交的冲突方收到明确的冲突错误，不静默覆盖
3. **Given** 一篇谱文，**When** 保存并刷新，**Then** 正文与分页结构一致
4. **Given** 一篇谱文，**When** 删除，**Then** 其分页与页面媒体按声明的删除语义级联或置空

---

### US-007（P1）多租户隔离

**作为**工作室管理员，**我希望**我的 Organization 完全看不到其他 Organization 的任何行，**以便**客户数据绝对不串。

**为什么是 P1**：这是 SaaS 的生死线。跨租户泄漏一次，产品即结束。

**独立测试**：建两个 Organization 各写一条人物 → 用 A 的会话查全部人物 → 只能看到 A 的。

**验收场景**：

1. **Given** 两个 Organization 各有数据，**When** A 组织成员查询列表，**Then** 结果不含 B 的任何行
2. **Given** B 组织的一条记录 ID，**When** A 组织成员直接按 ID 访问，**Then** 返回「不存在或无权」，不泄漏 B 的数据存在性
3. **Given** 应用代码漏写 `WHERE organization_id` 的一个查询，**When** 在真 PG 18 上执行，**Then** RLS 策略仍然过滤掉其他租户的行
4. **Given** 一个成员被移出 Organization，**When** 该成员用旧会话重试，**Then** 可见组织数组为空，读不到任何行
5. **Given** 一个只读角色，**When** 尝试写入，**Then** 被拒绝且错误明确

---

### US-008（P1）组织与谱项目生命周期

**作为**工作室管理员，**我希望**创建项目、邀请成员、归档组织，**以便**管理真实的修谱工作流程。

**为什么是 P1**：租户的组织结构是所有数据的挂载点，先于任何业务功能存在。

**独立测试**：创建组织 → 创建项目 → 邀请成员并接受 → 成员可访问该项目。

**验收场景**：

1. **Given** 一个已认证用户，**When** 创建 Organization，**Then** 创建者成为 `owner`
2. **Given** 一个 Organization，**When** 邀请一名成员，**Then** 邀请记录创建，成员接受后进入 `organization_member`
3. **Given** 一个 Organization，**When** 转移所有权，**Then** 所有权原子转移，并发转移时只有一个成功，其余收到明确错误
4. **Given** 一个 Organization，**When** 归档该组织，**Then** 组织进入归档状态，**数据不被物理删除**
5. **Given** 一个已归档组织，**When** 成员尝试写入，**Then** 写入被拒绝

---

### US-009（P3）编排谱书目录并导出不可变版本

**作为**修谱主事人，**我希望**编排谱书目录并导出一个不可变版本，**以便**底稿之后怎么改，已导出的文件不变。

**为什么是 P3**：出版是终点功能，依赖前面全部到位；且它有独立的复杂度（同步导出的上限），不适合早期。

**独立测试**：编排目录 → 导出一个版本 → 之后修改底稿 → 再看已导出文件，内容不变。

**验收场景**：

1. **Given** 一个谱书目录，**When** 导出，**Then** 生成一个 `book_release` 快照，版本号唯一且单调递增
2. **Given** 一个已导出版本，**When** 底稿内容被修改，**Then** 该版本内容不变
3. **Given** 一个谱书，**When** 两次并发导出，**Then** 版本号不冲突，后到者收到明确错误
4. **Given** 一个超出同步导出上限的谱书，**When** 导出，**Then** 明确拒绝并说明上限，而不是静默截断

---

### US-010（P3）媒体附件

**作为**修谱主事人，**我希望**上传家谱图片、老照片、扫描件并关联到人物或谱文，**以便**影像资料与文字记录在同一处。

**为什么是 P3**：媒体是横切关注点，且引入对象存储后有额外的访问控制面；先验证结构型功能。

**验收场景**：

1. **Given** 一个项目，**When** 通过服务端代理上传一个媒体文件，**Then** 文件进入私有桶并生成 `media_asset` 记录
2. **Given** 一个媒体资产，**When** 未授权用户尝试下载，**Then** 被拒绝（对象存储不做公开读）
3. **Given** 一条人物媒体关联，**When** 删除该关联，**Then** 媒体资产按声明的语义处理，不产生悬空引用

## 4. 关键实体（Key Entities）

> 完整字段定义见数据模型文档。此处只列**概念**与它们之间的关系。

| 实体                                 | 一句话定义               | 关键关系                              |
| ---------------------------------- | ------------------- | --------------------------------- |
| Organization                       | 租户，数据的最终归属          | 拥有 Project 与成员；拥有全部媒体             |
| Project                            | 一份谱的数据边界            | 隶属 Organization；拥有全部业务实体          |
| Person                             | 人物事实                | 隶属 Project；有多条姓名与关系               |
| Person Name                        | 人物的六类称谓之一           | 隶属 Person；至多一个主显示名                |
| Person Relation                    | 两个 Person 之间的封闭类型关系 | 隶属 Project；两端均为 Person            |
| Event                              | 人物相关的事件             | 隶属 Project；可挂来源引用                 |
| Lineage                            | 谱系（位置投影的容器）         | 隶属 Project；拥有 Node                |
| Node                               | 人物在谱系中的编纂位置         | 隶属 Lineage；引用 Person；含 `ltree` 路径 |
| Source / Source Citation           | 史料出处及其到实体的引用        | 隶属 Project；可指向 Person             |
| Article / Article Page             | 谱文与分页               | 隶属 Project；带版本列                   |
| Book / Book Catalog / Book Release | 谱书、编目树、不可变出版快照      | 隶属 Project；Release 引用 Catalog     |
| Media Asset                        | 私有媒体                | 隶属 Organization；可挂到人物或谱文页         |
| Audit Log                          | 只追加的审计记录            | 隶属 Organization                   |

**不作为实体存在的东西**（这是本文最容易被误加的部分）：

- **Family** —— 不建表。家庭是人物关系的组合视图（宪法 Article IV）。
- **兄弟姐妹 / 祖孙 / 世次** —— 不建表、不落库。由关系推导。
- **谱系位置的重复副本** —— 不存。`ltree` 路径是投影，不是事实。

## 6. 假设与依赖（Assumptions）


| 编号       | 假设                                  | 若不成立的后果                             |
| -------- | ----------------------------------- | ----------------------------------- |
| `ASM-01` | 谱牒是**低频编辑**场景，乐观锁足够，不需要实时协同         | 需引入 CRDT 或协同服务，复杂度预算（Article I）突破   |
| `ASM-02` | 一个 PostgreSQL 18 实例能装下十年的谱牒数据量      | 需分库分表，与「明确不做」直接冲突，须重新评估架构           |
| `ASM-03` | 团队 1–3 人，不具备独立运维微服务与消息队列的余量         | 架构须整体重估，不是局部调整                      |
| `ASM-04` | 关系类型集合在 V1 内稳定；新增类型是**例外事件**，不是常规需求 | 若需频繁扩展，封闭集合的约束收益被削弱，须重评 `FR-REL-01` |
| `ASM-05` | `pg_trgm` + `ILIKE` 足以支撑检索，无需独立搜索引擎 | 数据量或检索需求跃迁时须复评                      |
| `ASM-06` | 用户愿意上传史料影像到私有桶（信任服务端鉴权）             | 需引入直传 + 签名 URL，改变媒体架构               |
| `ASM-07` | 出版导出在同步请求上限内可完成；超大谱书是少数             | 需引入异步导出任务队列                         |

## 7. 边界情况（Edge Cases）

| 编号      | 情况                    | 期望行为                                                      |
| ------- | --------------------- | --------------------------------------------------------- |
| `EC-01` | 配偶关系两端对调后重复录入         | 拒绝（唯一约束）                                                  |
| `EC-02` | 关系两端指向同一个人（自环）        | 拒绝                                                        |
| `EC-03` | 血缘父母 + 收养父母 + 承嗣构成祖先环 | 拒绝写入，不产生任何位置投影                                            |
| `EC-04` | 继亲 / 寄养 / 监护构成环       | **允许**（不参与祖先环检测）                                          |
| `EC-05` | 只知父母一方                | 允许，另一方显示未知，不虚构人物                                          |
| `EC-06` | 删除谱系位置节点              | 节点删除，**人物保留**                                             |
| `EC-07` | 删除人物                  | 按声明的删除语义处理引用（`RESTRICT` / `CASCADE` / `SET NULL`），不留下悬空引用 |
| `EC-08` | 归档组织                  | 状态变更，数据物理保留；成员写入被拒绝                                       |
| `EC-09` | 成员被移出组织后重试旧会话         | 可见组织数组为空，读不到任何行                                           |
| `EC-10` | 越权按 ID 直接访问他租户记录      | 返回「不存在或无权」，不泄漏存在性                                         |
| `EC-11` | 两人同时编辑同一篇谱文           | 后提交者收到冲突错误，不静默覆盖                                          |
| `EC-12` | 两人同时转移组织所有权           | 仅一方成功，其余收到明确错误                                            |
| `EC-13` | 两人并发导出同一谱书            | 版本号唯一，后到者收到明确错误                                           |
| `EC-14` | 谱书超出同步导出上限            | 明确拒绝并说明上限，不静默截断                                           |
| `EC-15` | 非空文本字段传入纯空白字符串        | 被 `btrim(x) <> ''` 拒绝                                     |
| `EC-16` | 提交空姓名 / 空标题           | 同 `EC-15`                                                 |
| `EC-17` | 关系指向不存在的人物            | 外键拒绝                                                      |
| `EC-18` | 引用指向不存在的人物            | 外键拒绝（`FR-SRC-02`）                                         |
| `EC-19` | 应用连接池耗尽 / 锁等待超时       | `lock_timeout` 命中后返回明确错误，不挂死                              |
| `EC-20` | 已导出版本存在时，底稿目录被重构      | 已导出内容不变（`SC-EXT-01`）                                      |

## 8. 明确不做（V1 Out of Scope）

> **本节是「明确不做」清单的唯一权威副本。** `plan.md` 与 `data-model.md` **只引用编号，不复制表格**（宪法 Article VI）。  
> 每项都带复评触发条件——没有触发条件的「不做」就是懒政。

| 编号       | 不做                          | 理由                             | 复评触发条件                  |
| -------- | --------------------------- | ------------------------------ | ----------------------- |
| `OOS-01` | 独立 Family 实体                | 家庭是人物关系的组合视图，不另建表              | 出现无法用关系图表达的家族概念         |
| `OOS-02` | 兄弟姐妹 / 祖孙 / 叔伯 / 堂表亲的独立存储   | 可从关系推导，存两份必有一致性问题              | 推导成本在实测中不可接受            |
| `OOS-03` | 任意关系类型                      | 封闭集合才能做严格约束                    | `ASM-04` 失效             |
| `OOS-04` | 关系规则引擎                      | 规则已有执行者（DB 约束/触发器），引擎是第二真相源    | 出现需要用户自定义规则的明确需求        |
| `OOS-05` | 跨 Project 的人物主数据与自动合并       | 默认谱之间人物独立，合并需人工裁决              | 客户明确要求跨谱复用人物            |
| `OOS-06` | 软删除                         | 删除就是删除；归档与完成是业务状态              | 无。这是永久性决定               |
| `OOS-07` | 订阅计费                        | 当前产品不做计费                       | 商业模式确定要收费               |
| `OOS-08` | 微服务                         | 1–3 人团队切服务是把复杂度翻倍换零收益          | 团队规模或独立扩缩容需求改变          |
| `OOS-09` | 消息队列 / Redis / 任务框架         | 没有第二个消费方，队列就是负债                | 出现第二个消费方                |
| `OOS-10` | 搜索引擎（ES / Meilisearch）      | `pg_trgm` + `ILIKE` 足够且无额外运维成本 | `ASM-05` 失效             |
| `OOS-11` | 实时协同（CRDT / WebSocket 同步编辑） | 谱牒是低频编辑，乐观锁足够                  | `ASM-01` 失效             |
| `OOS-12` | SSR / SEO                   | 登录后的工具，搜索引擎不收录                 | 产品形态变为公开内容站点            |
| `OOS-13` | 可随意加列的通用表                   | 界面与 API 的形状是人物、关系、编纂位置         | 出现真正的异构业务实体             |
| `OOS-14` | 独立缓存层                       | 数据库就是缓存                        | 实测查询延迟不可接受              |
| `OOS-15` | 插件 / 脚本 / 工作流引擎             | 没有扩展需求，每个扩展点都是长期负债             | 出现第三方扩展的真实生态            |
| `OOS-16` | 多数据库 / 分库分表                 | 一个 PostgreSQL 能装下十年数据          | `ASM-02` 失效             |
| `OOS-17` | 第二套测试运行器                    | `bun test` 能连真 PG 跑集成          | 出现 `bun test` 无法覆盖的测试类型 |
| `OOS-18` | 多套画布渲染路径                    | 三条路径要三个人养，只做一条                 | 实测性能或交互需求确实需要第二条路径      |
| `OOS-19` | 对象存储公开读                     | 媒体访问必须经服务端鉴权                   | 无。这是永久性决定               |

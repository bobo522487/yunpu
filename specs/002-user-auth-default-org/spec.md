# Feature Specification: 用户注册、登录与默认组织

**Feature Branch**: `002-user-auth-default-org`

**Created**: 2026-11-14

**Status**: Draft

**Input**: User description: "用户的注册/登录/默认组织"

**基线与引用**: 本批次只引用 `docs/` 的既有结论，不复制表格。组织与成员边界见 [functional.md](../../docs/requirements/functional.md)（`FR-ORG-01`、`FR-ORG-02`、`FR-ORG-03`）与 [user-stories.md](../../docs/requirements/user-stories.md)（`US-007`、`US-008`）；认证与会话约定见 [overview.md](../../docs/architecture/overview.md) §10；邀请兑换规则见 [schema.md](../../docs/architecture/data/schema.md) §5.3（`DM-INV-01`~`05`）。本规格只定义「用户首次可用」这一段行为，不重复定义组织、成员与邀请的内部规则。

## 术语

- **账号**：一个可以用邮箱与密码证明身份的用户身份。邮箱在系统内唯一。
- **会话**：一次登录产生的、可被持续验证的登录状态。它决定当前请求以哪个账号的身份执行。
- **组织（Organization）**：租户，是数据与成员的归属单位。每个组织恰好有一个 owner。
- **成员**：账号与组织的归属关系，成员在组织内具有 `admin` / `editor` / `viewer` 之一的角色；owner 始终按 `admin` 对待，且不是一种成员角色。
- **默认组织**：账号登录后自动进入的那个组织。它是账号的一个指针，不是第二份组织事实。
- **引导状态**：账号当前没有任何可用组织时的状态。此时不进入任何组织的工作区，只提供创建或加入组织的入口。
- **可用组织**：状态为 active 的组织。已归档组织不算可用组织。

## Clarifications

### Session 2026-11-14

- Q: 本批次的登录方式是否只包含邮箱与密码，还是同时包含微信 OAuth？ → A: 仅邮箱与密码；微信 OAuth 不在本批次。
- Q: 「上次使用的组织」这一记忆需要在不同设备之间同步，还是只记住当前这台设备？ → A: 跨设备同步，默认组织属于账号级偏好。
- Q: 登录失败是否需要按账号或来源做临时限流，还是只依赖平台统一的请求限流？ → A: 同一邮箱 + 来源地址连续 5 次失败后，15 分钟内拒绝该组合的登录尝试。
- Q: 会话除了既有的 7 天滑动有效期外，是否还需要一个绝对最长寿命？ → A: 不设绝对上限，持续活跃即按 7 天滑动续期。
- Q: 注册时是否要求用户填写显示名，还是只凭邮箱与密码完成注册？ → A: 注册只要求邮箱与密码，显示名可后续设置。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 注册后立即获得一个默认组织 (Priority: P1)

一位第一次使用产品的修谱主事人，在注册页用邮箱和密码完成注册。注册成功后，他不需要再做任何配置，就直接进入一个属于他自己的组织工作区；他是这个组织的 owner。整个过程不出现「注册成功但不知道下一步做什么」的中间状态。

**Why this priority**: 这是产品从「未登录」到「可开始工作」的唯一入口。没有默认组织，注册完成后用户看到的是空页面，后续所有业务功能都没有数据挂载点。文档中「Organization 是所有数据的挂载点」在此落地。

**Independent Test**: 用一个全新邮箱完成注册，确认会话已建立、默认组织已存在、当前账号是该组织的 owner，并且可以直接在该组织下创建第一个项目。

**Acceptance Scenarios**:

1. **Given** 一个未注册的邮箱，**When** 用户提交邮箱与符合要求的密码完成注册，**Then** 账号被创建，会话立即建立，用户无需再次登录即可进入工作区。
2. **Given** 注册请求合法且不携带任何邀请，**When** 注册完成，**Then** 系统自动创建一个默认组织，注册者成为该组织唯一的 owner，并以 `admin` 权限出现在成员中。
3. **Given** 注册同时触发账号与默认组织的创建，**When** 其中任一步失败，**Then** 整个注册失败并明确报错，不得出现「账号已创建但没有默认组织」或「组织已创建但没有 owner」的半成品。
4. **Given** 注册成功，**When** 用户进入默认组织，**Then** 默认组织名称有可读的默认值，且允许用户后续修改；名称允许与其他组织重名。
5. **Given** 一个已存在的邮箱，**When** 另一位用户尝试用同一邮箱注册，**Then** 注册被拒绝，错误提示不泄漏该邮箱下账号的敏感信息，且不创建任何账号或组织。

### User Story 2 - 登录、登出与会话保持 (Priority: P1)

一位已有账号的修谱主事人，在任意设备上用邮箱和密码登录，直接回到自己的默认组织继续工作。关闭页面后再次打开，只要会话仍在有效期内，就不需要重新登录。完成工作后可以主动登出；登出只结束当前这次会话，不影响同一账号在其他设备上的会话。

**Why this priority**: 注册只发生一次，登录却每天发生。登录失败或会话无故丢失，会让用户无法进入已有数据，等价于数据不可用。

**Independent Test**: 用已注册账号登录，确认回到默认组织；关闭并重新打开产品，确认仍处于登录状态；登出后确认需要重新登录，而另一台设备上的会话不受影响。

**Acceptance Scenarios**:

1. **Given** 一个已注册账号，**When** 用户提交正确的邮箱与密码，**Then** 登录成功并进入该账号的默认组织。
2. **Given** 邮箱不存在或密码错误，**When** 用户尝试登录，**Then** 登录失败，两种原因返回一致的外部提示，不暴露该邮箱是否已注册。
3. **Given** 登录成功，**When** 用户在会话有效期内再次打开产品，**Then** 无需重新输入凭证即恢复登录状态。
4. **Given** 用户持续活跃使用产品，**When** 会话接近有效期，**Then** 会话在活动中被续期，用户不会在工作过程中被无预警登出。
5. **Given** 会话已过期或已被登出，**When** 用户访问需要登录的页面或操作，**Then** 请求被拒绝并引导重新登录，不返回任何组织数据。
6. **Given** 同一账号在两台设备上登录，**When** 用户在设备 A 登出，**Then** 设备 B 的会话仍然有效。
7. **Given** 用户主动登出，**When** 登出完成，**Then** 当前会话立即失效，浏览器无法再用它访问受保护内容。

### User Story 3 - 通过邀请注册或登录时进入正确的组织 (Priority: P2)

一位被邀请加入某组织的新成员，从邀请链接进入产品。如果他还没有账号，注册完成后应直接成为该组织的成员，并把该组织作为默认组织，而不是另外创建一个空组织。如果他已经有账号，登录后接受邀请，并把默认组织切换到邀请所属的组织。

**Why this priority**: 邀请是组织扩充成员的正常路径。若邀请注册总是产生一个多余的个人组织，成员会长期在错误的租户里工作，数据也挂错地方。

**Independent Test**: 用与邀请邮箱一致的新邮箱通过邀请链接注册，确认账号只加入邀请组织、默认组织就是该组织、且没有额外创建个人组织；再用已注册账号接受另一组织的邀请，确认默认组织随之切换。

**Acceptance Scenarios**:

1. **Given** 一个邮箱与邀请邮箱一致的新用户，**When** 通过邀请链接完成注册，**Then** 邀请被兑换，用户成为邀请组织的成员，默认组织为该邀请组织，且不额外创建个人默认组织。
2. **Given** 一个已有账号且已登录的用户打开邀请链接，**When** 接受邀请，**Then** 用户加入该组织，默认组织切换为该组织。
3. **Given** 注册时填写的邮箱与邀请邮箱不一致，**When** 注册完成，**Then** 注册本身成功，邀请不被兑换，界面明确说明「邀请与当前邮箱不匹配」，并按无邀请注册处理（创建个人默认组织）。
4. **Given** 邀请已过期、已撤销或已被兑换，**When** 用户通过该链接注册或接受邀请，**Then** 明确提示邀请不可用，注册不因此失败，也不产生对该组织的成员关系。
5. **Given** 同一个邀请被两个人先后兑换，**When** 第二个请求到达，**Then** 只有一人加入组织，另一人收到明确的「邀请已被使用」错误，不产生重复成员。

### User Story 4 - 多组织下的默认组织选择与切换 (Priority: P2)

一位同时属于多个组织的用户，每次登录都回到自己上次工作的那个组织，而不是每次都回到最早创建的组织。当他想去另一个组织时，可以在工作区内切换；切换结果会被记住，下次登录仍然进入这个组织。

**Why this priority**: 多组织是工作室协作的常态。若默认组织选择随机或固定，用户每天都要手动切换一次，长期成本高，也容易在错误的租户下编辑数据。

**Independent Test**: 一个账号加入两个组织，先在组织 B 工作后登出再登录，确认进入组织 B；再把组织 B 归档，重新登录后确认进入组织 A 而不会进入已归档组织。

**Acceptance Scenarios**:

1. **Given** 用户属于多个组织且存在上次使用的组织，**When** 登录，**Then** 默认组织为上次使用的组织。
2. **Given** 用户属于多个组织但没有任何使用记录，**When** 首次登录，**Then** 默认组织为其最早加入的可用组织。
3. **Given** 用户在组织 A 工作后切换到组织 B，**When** 用户登出后重新登录，**Then** 默认组织为组织 B。
4. **Given** 用户的默认组织已被归档，**When** 登录，**Then** 系统跳过该组织，改选其他可用组织，不把已归档组织作为默认组织。
5. **Given** 用户不属于任何可用组织（例如已被移出全部组织），**When** 登录，**Then** 进入引导状态，提供创建组织与接受邀请的入口；不静默创建新组织。
6. **Given** 用户切换到非默认组织，**When** 用户在该组织内操作，**Then** 所有数据访问都限定在该组织内，不出现跨组织数据混用。
7. **Given** 用户在设备 A 把默认组织切换为组织 B，**When** 用户随后在设备 C 登录，**Then** 默认组织同样为组织 B，不需要在设备 C 重新切换。

### Edge Cases

- 注册时邮箱只做了大小写或首尾空白的差异（如 `User@X.com ` 与 `user@x.com`）：视为同一邮箱，不允许注册出两个账号。
- 同一邮箱在极短时间内被并发提交多次注册：最多一个成功，其余收到明确的「邮箱已注册」错误，不产生重复账号或重复默认组织。
- 注册时密码为空、仅空白或低于最低强度：注册被拒绝并明确说明要求，不创建账号，也不创建默认组织。
- 注册默认组织创建过程中失败：整个注册回滚，用户可以用同一邮箱重试，不留下占用邮箱却没有组织的账号。
- 邀请注册中邀请兑换失败（邮箱不匹配、过期、已撤销、已兑换）：注册不失败，但邀请不生效并有明确提示；用户按无邀请注册进入自己的默认组织。
- 会话过期发生在保存操作中途：操作被拒绝并提示重新登录；不得把未保存的内容当作已保存。
- 会话凭据被伪造或无效：视为未登录，返回「需要登录」，不泄漏任何账号或组织信息。
- 同一组合达到失败上限后，用户改用另一来源地址或稍后重试：限流只针对原组合，窗口结束后自动解除，不需要人工解锁或修改密码。
- 攻击者在多个来源地址之间轮换同一邮箱：本规则按组合计数，不承诺拦截这种轮换；平台统一请求限流仍作为兜底。这是已接受的边界，不是遗漏。
- 账号在另一处被停用或删除后仍持有旧会话：下一次访问被拒绝，不继续返回数据。
- 用户的默认组织被归档后，恰好在另一个标签页继续操作：该标签页的写入被拒绝，并引导切换到其他可用组织。
- 用户被移出组织后，其默认组织指针仍指向该组织：登录时跳过它，进入引导状态或其他可用组织。
- 组织 owner 的成员关系受保护（不可被移出），因此 owner 的默认组织只会在组织归档时失效。
- 系统时间或时区变化导致会话有效期判断偏差：以统一的服务端时间为准，不因客户端时间被篡改而延长会话。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 系统必须允许仅凭邮箱与密码创建账号，不要求填写显示名等其他资料。邮箱在存储前统一去除首尾空白并转为小写，且全系统唯一。
- **FR-002**: 系统必须拒绝空密码、纯空白密码和长度低于 8 个字符的密码，并在失败提示中说明最低要求。
- **FR-003**: 系统不得以可直接还原明文的方式保存密码；任何日志、错误信息与审计载荷都不得出现密码原文。
- **FR-004**: 注册成功后系统必须立即建立登录会话，用户无需二次登录即可进入工作区。
- **FR-005**: 注册请求不携带有效邀请时，系统必须在同一次注册中创建一个默认组织，并把注册者设为该组织唯一的 owner 与 `admin` 成员。
- **FR-006**: 账号创建与默认组织创建必须具备一致性：任一步失败则整体失败，系统中不得存在「有账号无默认组织」或「有组织无 owner」的中间态。
- **FR-007**: 默认组织必须有可读的默认名称，名称由已设置的显示名或邮箱前缀生成；名称允许重复，并允许创建者后续修改。
- **FR-008**: 系统必须支持用邮箱与密码登录；登录成功后进入该账号的默认组织。
- **FR-009**: 登录失败时，系统必须对「邮箱不存在」与「密码错误」返回一致的外部提示，不暴露邮箱是否已注册。
- **FR-010**: 会话必须具有明确的有效期，并在用户持续活动时按约定续期；有效期与续期窗口以系统统一时间为准，不采用客户端时间；本批次不设绝对最长寿命。
- **FR-011**: 系统必须支持主动登出；登出只使当前这一次会话失效，不影响同一账号在其他设备上的会话。
- **FR-012**: 未登录或会话已失效的请求访问受保护内容时，系统必须拒绝并引导重新登录，且不返回任何组织或业务数据。
- **FR-013**: 系统必须为每个账号维护跨设备一致的「默认组织」指针；登录时按「上次使用的可用组织 → 最早加入的可用组织 → 引导状态」的顺序解析。
- **FR-014**: 已归档组织不得被解析为默认组织；用户在某组织内切换后，切换结果必须被记住并用于下一次登录。
- **FR-015**: 用户不属于任何可用组织时，系统必须进入引导状态，提供创建组织与接受邀请的入口，且不得静默创建新组织。
- **FR-016**: 通过携带有效邀请的注册，系统必须在校验邮箱与邀请邮箱一致后兑换邀请，使用户加入邀请组织，并以该组织作为默认组织，且不额外创建个人组织。
- **FR-017**: 邀请兑换失败不得导致注册失败；系统必须明确提示失败原因，并按无邀请注册处理。
- **FR-018**: 同一邀请只能被成功兑换一次；并发兑换时只有一方成功，其余收到明确错误，且不产生重复成员。
- **FR-019**: 组织内的所有操作必须限定在当前会话所属的组织内；默认组织的选择不得成为绕过组织边界的入口。
- **FR-020**: 注册、登录、登出与邀请兑换的关键事件必须留下可审计的记录；记录中不得包含密码、会话令牌或邀请明文。
- **FR-021**: 系统必须按「同一邮箱 + 同一来源地址」统计连续登录失败：连续 5 次失败后，15 分钟内拒绝该组合的登录尝试；成功登录后计数清零；限流期间的拒绝提示不得区分邮箱是否存在。

### Key Entities *(include if feature involves data)*

- **账号**：登录身份。关键属性包括规范化后的唯一邮箱、不可还原的密码凭证、显示名（可缺省，缺省时为邮箱前缀）与可用状态。一个账号可属于多个组织。
- **会话**：一次登录的有效状态。关键属性包括所属账号、创建时间、最近活动时间、过期时间与状态。一个账号可有多个并存会话。
- **组织（Organization）**：租户。关键属性包括名称、状态（active / suspended / archived）与唯一 owner。组织归档是状态变化，不是删除。
- **组织成员**：账号与组织的归属关系。关键属性包括组织、账号与角色（`admin` / `editor` / `viewer`）。owner 不是成员角色。
- **邀请**：指向某个邮箱与某个组织的加入凭据。关键属性包括目标邮箱、目标组织、拟授予角色、状态与有效期。邀请不能授予 owner。
- **默认组织指针**：账号级的偏好，指向该账号下次登录时应进入的组织，跨设备一致。它不是组织事实的第二份存储，组织被归档或成员关系消失时该指针自动失效。
- **登录失败计数**：按「邮箱 + 来源地址」组合在滚动窗口内的临时状态，仅用于拦截连续失败尝试。它不是账号的长期属性，窗口结束或登录成功后即失效。

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 新用户从打开注册页到进入默认组织工作区，中位耗时不超过 2 分钟；首次尝试成功率不低于 95%。
- **SC-002**: 注册成功但未获得默认组织的账号数为 0；默认组织存在但没有 owner 的组织数为 0。
- **SC-003**: 同一邮箱并发提交 10 次注册时，成功创建的账号数恰好为 1，其余 9 次均返回明确错误。
- **SC-004**: 已注册用户登录后进入默认组织的中位耗时不超过 3 秒，95% 的登录不超过 5 秒。
- **SC-005**: 携带有效邀请注册的用户中，100% 加入邀请组织且不被额外创建个人组织；邮箱不匹配时误加入组织的比例为 0。
- **SC-006**: 会话过期或登出后的受保护请求，100% 被拒绝并引导登录，返回的业务数据记录数为 0。
- **SC-007**: 属于多个组织的用户，登录后进入上次使用组织的比例 100%；没有任何使用记录时进入最早加入组织的比例 100%；在同一账号的另一台设备上登录时，进入同一默认组织的比例 100%。
- **SC-008**: 已归档组织被解析为默认组织的次数为 0；无可用组织时用户进入引导状态的比例 100%。
- **SC-009**: 登录失败响应中能够区分「邮箱是否存在」的响应比例为 0。
- **SC-010**: 同一「邮箱 + 来源地址」组合连续失败 5 次后，15 分钟窗口内的后续登录尝试 100% 被拒绝；窗口结束后无需人工解锁即可再次尝试；期间有一次成功登录时计数立即清零。
- **SC-011**: 持续活跃的会话不会因绝对时长被强制中断；会话失效只来自超过 7 天无活动、主动登出或账号状态变化，符合该来源的会话失效比例为 100%。
- **SC-012**: 仅填写邮箱与密码即可完成注册的用例比例为 100%；注册路径中要求额外必填资料的步骤数为 0。

## Assumptions

- 本批次登录方式确定为仅邮箱与密码（2026-11-14 澄清），覆盖注册、登录、登出与会话保持。微信 OAuth、邮箱验证、找回密码与修改密码不在本批次内，作为后续批次依据同一账号模型扩展。
- 产品当前没有邮件发送基础设施，因此注册后不要求邮箱验证，也不提供邮件找回密码。这是范围选择，不是遗漏。
- 注册只要求邮箱与密码（2026-11-14 澄清），显示名不参与注册校验；未设置显示名时以邮箱前缀作为可读标识，用户可在账号设置中补充或修改。
- 会话有效期与续期窗口沿用 [overview.md](../../docs/architecture/overview.md) §10 的既有约定（7 天有效期、滑动续期 1 天），且不设绝对最长寿命（2026-11-14 澄清）；本批次不重新定义有效期数值。
- 「注册即创建默认组织」只适用于没有有效邀请的注册；通过邀请注册的用户以邀请组织为默认组织，避免产生无人使用的空组织。
- 「默认组织」是账号偏好，不是组织事实；允许账号在成员关系消失或组织归档后暂时没有默认组织，此时进入引导状态。
- 默认组织名称由系统按可读规则生成（例如包含用户显示名或邮箱前缀），允许重名，用户可在组织设置中修改。
- 邀请的生成、撤销与消息投递属于组织模块；本批次只负责在注册或登录后消费邀请并正确落到默认组织，邀请规则以 `DM-INV-01`~`05` 为准。
- 审计记录沿用既有审计边界：组织创建、邀请兑换等强审计动作由组织模块执行；本批次不新增审计存储。
- 本批次不引入缓存、消息队列、独立认证服务或第二个数据库；认证数据与其他业务数据同属现有数据库边界。
- 本批次不实现永久账号锁定、图形验证码或多因素认证。登录失败防护确定为「同一邮箱 + 来源地址连续 5 次失败后 15 分钟内拒绝」（2026-11-14 澄清）；平台统一请求限流继续作为兜底。
- 默认组织属于账号级偏好，跨设备一致（2026-11-14 澄清）。同一账号在多台设备上并发切换组织时，以最后一次成功写入为准；不要求实时推送到其他已打开的页面。

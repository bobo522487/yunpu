# 组织与成员协作

> 本文件只描述业务行为、规则与验收契约，不包含数据库语句、框架名、内部类名、配置或接口路径等技术实现细节。关键业务规则以需求方已确认的「A 收敛」方向为准；未确认项不得自行推断补全。账号注册、登录、默认组织解析与邀请兑换的落位行为见 `002-user-auth-default-org`，本文件不重复定义。

## 1. Overview

本功能定义「一个组织如何被人协作地拥有和维护」：邀请协作者加入、分配职责、调整与移除成员、移交所有权、维护组织信息并归档。目标是让修谱主事人能把一个组织从「只有自己」带到「多人各司其职」，同时全程不越出租户边界，不产生「无主组织」「幽灵成员」或「跨组织可见」。

设计取向（Linus 式收敛）：不增加新概念；把散落在多处的所有权约束收成**一条不变量**；删除事实上不可达的组织状态。已归档的 002 所定义的语义一律保留。

- **使用场景**
  - owner / admin 邀请新成员加入组织并指定职责；查看邀请状态并撤销尚未使用的邀请。
  - admin 调整成员角色、移除成员；成员主动退出组织。
  - owner 把所有权移交给另一名成员；移交后可退出。
  - owner 修改组织名称、归档组织；成员查看自己所属组织并切换当前工作组织。
  - 受邀者兑换邀请进入组织（兑换的落位与默认组织切换行为见 002；本文件只定义邀请侧的状态变化）。
- **非目标（Out of Scope）**
  - 组织删除与恢复；`suspended` 状态。
  - 邀请的邮件、短信或其他外部消息投递——邀请链接由调用方自行传递。
  - 谱系项目、人物、姓名、关系与投影的业务规则（后续独立功能）。
  - 账号注册、登录、会话、默认组织指针与邀请兑换的落位（见 002）。
  - 前端页面、路由、构建与托管；缓存、消息队列、独立权限服务或第二个数据库。
  - 跨源来源校验与会话防护（独立功能）。

## 2. User Stories

- **US-01（P1）**：作为组织的 owner 或 admin，我希望邀请协作者加入并指定职责，以便把修谱工作分派出去，而不必共享账号。
  - **独立验证**：创建一封新邮箱的邀请，确认邀请链接只在创建时出现一次、列表中不含可兑换凭据；兑换后确认新成员以指定角色进入该组织，且邀请变为已使用、不能再次兑换。
- **US-02（P1）**：作为组织的 admin，我希望调整成员角色或移除不再协作的成员，以便团队变更时权限跟着变。
  - **独立验证**：把一名成员从 viewer 改成 editor 后，确认其能写不能管；移除该成员后，确认其立即不再具有该组织的任何权限，且 owner 无法被移除或降级。
- **US-03（P1）**：作为组织 owner，我希望把所有权移交给另一位成员并随后退出，以便组织不会因我离开而失去归属。
  - **独立验证**：把所有权移交给一名 viewer，确认该成员自动按 admin 对待、原 owner 变为普通成员；随后原 owner 可以退出；归档组织不可移交。
- **US-04（P2）**：作为组织 owner，我希望修改组织名称并在完成时归档组织，以便组织信息准确且停止写入。
  - **独立验证**：改名后成员看到新名称；归档后所有写入被拒、组织不再出现在可选工作组织中、且不可重命名或再次移交。
- **US-05（P2）**：作为同时属于多个组织的成员，我希望查看自己所在的组织并在其中切换，以便知道自己在为哪个组织工作。
  - **独立验证**：列出时只看到 active 组织及自己在其中的角色；切换后当前组织立即改变，且切换不影响默认组织的跨设备语义（见 002）。
- **US-06（P1）**：作为租户边界的守护者，我希望所有成员、邀请与所有权操作都限定在当前组织内，且变更要么全成要么全不成，以便不会出现跨组织数据或未完成的状态。
  - **独立验证**：以 A 组织成员身份操作 B 组织，一律得到「不存在或无权」且无法区分两种情况；人为让一次变更在中途失败，确认没有任何部分生效。

## 3. Functional Requirements

> 每条需求使用唯一 ID，并附带可直接观察、可独立验证的验收标准。

### FR-001：组织创建与唯一 owner
- 系统必须允许已登录用户创建一个新的 Organization。
- 每个 Organization 必须恰好有一个 owner；创建者即为该组织的 owner。
- owner 以 `admin` 角色出现在成员中，但「所有者」不等于「admin 角色」，而是组织上的一项归属关系。
- **验收标准**：Given 一个新建组织，When 查看其成员与归属，Then 恰好一名 owner 且该 owner 的角色为 `admin`；系统中不存在没有 owner 的组织。

### FR-002：所有权是唯一不变量
- 所有权只能通过 FR-003 的移交解除。不得以移除成员、主动退出、降低角色、归档以外的任何方式让组织失去 owner。
- 因此 owner 不可被移除、不可主动退出、不可被降级为非 `admin` 角色；owner 也不能被直接授予第二份所有权。
- 上述禁止不是多条独立规则，而是「所有权只能靠移交解除」这一条规则的必然结果。
- **验收标准**：分别尝试移除 owner、让 owner 退出、把 owner 角色改为 `editor` 或 `viewer`，Then 三种操作全部被拒绝且组织 owner 不变；除成功移交外，owner 发生变化的组织数为 0。

### FR-003：所有权移交
- 系统必须允许 owner 把所有权移交给同一组织内的另一名成员。
- 接收方必须是该组织的成员；接收方若原为 `viewer` 或 `editor`，移交成功后自动按 `admin` 对待。
- 移交成功后原 owner 失去所有者身份，成为普通成员，其原有成员角色不变。
- archived 组织不可移交。
- 并发移交时最多一个成功，其余得到明确冲突错误。
- **验收标准**：Given 一名 owner 与一名 viewer 成员，When 成功移交，Then 新 owner 按 `admin` 对待、原 owner 不再为 owner 且成员角色未变；Given 两次并发移交，Then 恰好一次成功；Given 归档组织，Then 移交被拒。

### FR-004：角色与权限边界
- 成员角色为 `admin`、`editor`、`viewer` 三种，含义固定：`admin` 可管理成员、邀请与组织设置并可移交所有权；`editor` 可读写谱系业务数据但不可管理成员与组织设置；`viewer` 只读。
- owner 在所有管理操作中等同 `admin`，无需额外授权。
- 邀请不得授予 owner（owner 不是成员角色）。
- **验收标准**：分别以 admin、editor、viewer 身份执行成员管理与邀请管理，Then 仅 admin（及 owner）成功、editor 与 viewer 被拒且返回无权限错误；以任意角色创建邀请时，可授予角色只有三种成员角色。

### FR-005：跨租户隔离
- 所有成员、邀请、所有权与组织设置操作必须限定在请求所属组织内。
- 对非成员组织执行任何操作，一律返回「目标不存在或无权」，且不泄漏该组织是否存在、成员是谁或邀请内容。
- **验收标准**：Given A 组织成员对 B 组织的组织详情、成员列表、邀请列表、移交、改名、归档等操作，Then 全部返回同一种「不存在或无权」错误，响应中不含任何 B 组织数据。

### FR-006：所属组织列表与当前组织切换
- 系统必须允许已登录成员查看自己所属的全部 active 组织及自己在每个组织中的角色与所有者身份。
- 成员可以在其 active 组织之间切换当前工作组织；切换成功后立即以新组织作为当前组织。
- archived 组织不得出现在列表中，也不可被切换进入。
- **验收标准**：Given 一名成员属于一个 active 与一个 archived 组织，When 列出组织，Then 只返回 active 组织；切换到该组织后当前组织立即改变；尝试切换 archived 组织被拒。

### FR-007：组织名称维护
- `admin`（及 owner）可以修改组织名称；名称非空且在约定长度内。
- 组织名允许与其他组织重名。
- archived 组织不可改名。
- **验收标准**：Given 一个 active 组织，When 以 admin 改名，Then 所有成员看到新名称；Given 空名称或超长名称，Then 校验失败且不生效；Given archived 组织，Then 改名被拒。

### FR-008：组织归档
- `admin`（及 owner）可以把 active 组织归档；归档是状态变化，不是删除。
- 归档后组织为只读：谱系业务写入、成员与邀请管理、所有权移交、改名、再次归档均被拒绝；成员仍可读取（若业务允许）。
- 归档组织不得作为当前组织或默认组织，也不得再接受邀请兑换。
- **验收标准**：Given 一个已归档组织，When 执行任何写入或管理操作，Then 全部被拒；该组织不出现在所属组织列表中；原有数据仍可读取且未被删除。

### FR-009：组织状态只有 active 与 archived
- 本产品的组织状态只有 `active` 与 `archived` 两种；不存在 `suspended` 状态。
- 组织在创建时为 `active`，只能通过归档进入 `archived`，且不能从 `archived` 回到 `active`。
- **验收标准**：Given 任意组织，When 查询或设置其状态，Then 可观测状态仅为 `active` 或 `archived`；不存在任何手段使组织进入第三种状态或由 archived 恢复。

### FR-010：成员列表
- `admin`（及 owner）可以分页查看组织成员，每项包含成员身份、姓名、邮箱、角色、是否为 owner 与加入时间。
- 列表不得暴露任何邀请凭据（见 FR-014）。
- 非成员或无权限成员不可读取成员列表。
- **验收标准**：Given 一个含 owner 与两名成员的组织，When 以 admin 分页列出，Then 每人字段完整且 owner 标识正确；响应中不含任何邀请 token；以 viewer 访问被拒。

### FR-011：成员角色调整
- `admin`（及 owner）可以调整其他成员的角色为三种之一。
- owner 的角色不可被调整（FR-002）。
- 目标不是该组织成员时，返回「目标不存在或无权」，不泄漏区分信息。
- **验收标准**：Given 一名 editor 成员，When 改为 viewer，Then 其写权限立即消失；When 尝试改 owner 角色，Then 被拒；When 目标非成员，Then 返回「不存在或无权」。

### FR-012：成员移除
- `admin`（及 owner）可以移除其他成员；owner 不可被移除（FR-002）。
- 移除成功后该成员立即失去该组织的一切权限，其在该组织内的当前工作组织状态随之失效。
- 目标非成员时返回「不存在或无权」。
- **验收标准**：Given 一名成员被移除，When 其再次以该组织身份操作，Then 全部被拒；Given 移除 owner 或非成员，Then 分别被拒且成员列表不变。

### FR-013：成员主动退出
- 非 owner 成员可以主动退出组织；owner 不可退出（FR-002）。
- 退出成功后该成员不再属于该组织，其默认组织指针按 002 的规则重新解析。
- **验收标准**：Given 一名非 owner 成员退出，When 重新查询其所属组织，Then 不含该组织；Given owner 退出，Then 被拒。

### FR-014：邀请创建
- `admin`（及 owner）可以为指定邮箱创建邀请，并指定 `viewer`、`editor` 或 `admin` 之一作为拟授予角色；未指定角色时按最小权限 `viewer` 授予。
- 邀请有效期为 7 天，自创建时起算；过期后不可兑换。
- 同一组织内，同一邮箱同时最多只能有一个待处理邀请；重复创建返回冲突。
- 邀请只能授予成员角色，永不授予 owner。
- 可兑换凭据（邀请链接中的 token）只在创建成功的那一次响应中返回，之后任何列表或详情都不再返回；系统不得提供从其他字段反推凭据的途径。
- archived 组织不可创建邀请。
- **验收标准**：Given 创建一个未指定角色的邀请，When 兑换，Then 新成员角色为 `viewer`；Given 同一邮箱第二个待处理邀请，Then 冲突且不生成；Given 创建成功后查询列表与详情，Then 均不含可兑换凭据；Given archived 组织，Then 创建被拒。

### FR-015：邀请列表与状态
- `admin`（及 owner）可以分页查看组织邀请，每项包含邮箱、拟授予角色、状态（待处理 / 已使用 / 已撤销）、有效期与创建时间。
- 列表不得暴露可兑换凭据。
- 非 admin 成员不可读取邀请列表。
- **验收标准**：Given 组织有三类状态的邀请，When 以 admin 列出，Then 状态准确且无凭据字段；When 以 viewer 列出，Then 被拒。

### FR-016：邀请撤销
- `admin`（及 owner）可以撤销一个待处理的邀请；撤销后该邀请不可再兑换。
- 只能撤销待处理邀请；已使用或已撤销的邀请不可再次撤销。
- 非 admin 成员不可撤销；跨租户操作按 FR-005 处理。
- **验收标准**：Given 撤销一个待处理邀请后尝试兑换，Then 兑换被拒；Given 二次撤销或撤销已使用邀请，Then 被拒且状态不变。

### FR-017：邀请兑换的邀请侧状态
- 有效邀请被兑换后，邀请状态由「待处理」变为「已使用」，且不可再次兑换。
- 兑换的邮箱必须与邀请邮箱一致；不一致时邀请不变、按 002 的失败处理执行。
- 并发兑换时最多一个成功，其余收到「已被使用」错误，且不产生重复成员。
- 兑换后的成员落位、角色生效与默认组织切换遵循 002。
- **验收标准**：Given 两名用户并发兑换同一邀请，Then 恰好一人成功、邀请变为已使用、组织中只新增一名成员；Given 邮箱不匹配，Then 邀请仍为待处理。

### FR-018：变更原子性
- 成员、邀请、所有权与组织设置的每一次变更必须要么全部生效、要么全部不生效。
- 不得出现「成员关系已改但权限未同步」「所有权已变但角色未提升」「审计未记录但业务已生效」等中间态。
- **验收标准**：Given 在一次成员移除中人为使后续步骤失败，Then 该成员关系仍然存在且无部分生效痕迹；对所有写操作重复该验证，失败时状态与操作前一致。

### FR-019：并发一致性
- 同一组织的并发成员变更、邀请兑换与所有权移交必须产生确定结果：冲突方收到明确错误，不产生重复成员、重复邀请或多个 owner。
- **验收标准**：Given 并发执行同一目标的多写操作，Then 成功后组织中该目标只存在一份，冲突方均收到明确错误。

### FR-020：关键事件可审计且脱敏
- 邀请创建 / 撤销 / 兑换、成员角色调整 / 移除、所有权移交、组织归档必须留下可审计记录。
- 记录中不得包含邀请凭据、会话令牌或密码原文；必须能识别操作者、目标、动作与时间。
- **验收标准**：Given 依次执行上述动作，When 查询审计记录，Then 每个动作有对应记录且字段完整；所有记录中均不包含凭据、令牌或密码。

## 4. Business Rules

- **所有权（单一不变量）**：每个 Organization 恰好一个 Owner；所有权只能靠移交解除。owner 不可被移除、退出或降级——这不是三条特例，而是该不变量的推论。Owner 按 `admin` 对待，但「所有者」不是成员角色。
- **角色**：`admin` 管理成员 / 邀请 / 设置 / 移交；`editor` 读写谱系数据；`viewer` 只读。邀请不得授予 Owner。移交使接收方自动按 `admin` 对待。
- **生命周期**：Organization 只有 `active` 与 `archived`；归档是单向状态变化、不是删除；archived 只读、不可进入、不可移交、不可改名、不可邀请。`suspended` 不属于本产品状态。
- **邀请**：指定邮箱、指定成员角色、7 天有效、一次性兑换、同组织同邮箱仅一个待处理、永不授予 Owner、只可撤销待处理、凭据只下发一次。
- **租户边界**：所有操作限定在当前组织；跨租户一律「不存在或无权」，不泄漏存在性。
- **一致性**：写操作原子；并发写结果唯一。
- **不可变**：组织归属创建后不可变更；归档不可撤销；已使用邀请不可重置为待处理。
- **兼容**：002 已定义的注册 / 登录 / 默认组织 / 邀请落位语义不变；本功能不重复定义也不推翻它们。
- **删除特殊情况**：不引入第五种角色、不恢复 `suspended`、不新增「特邀成员」「临时管理员」等平行概念。

## 5. Exception Handling

- 目标组织不存在、调用方非成员、或权限不足：返回 `404 NOT_FOUND`，文案统一为「目标不存在或无权」，不区分三种情况。
- 参数缺失、格式非法、名称为空或超长：返回 `400 VALIDATION`，不创建任何资源。
- 尝试移除 / 降级 / 让 owner 退出：返回 `409 CONFLICT`，提示先移交所有权（仅退出场景）或说明所有者受保护。
- 对 archived 组织执行写入或管理操作：返回 `409 CONFLICT`，提示组织已归档。
- 创建邀请时同一邮箱已有待处理邀请：返回 `409 CONFLICT`。
- 邀请不存在、已过期或已被撤销：兑换返回 `404 TARGET_INVALID`，邀请状态不变。
- 邀请邮箱与兑换者不一致：返回 `403 INVITE_EMAIL_MISMATCH`，注册 / 落位按 002 继续，邀请保持待处理。
- 并发兑换同一邀请或并发移交所有权：成功方返回正常结果，其余返回 `409 CONFLICT`。
- 移交目标不是组织成员：返回 `404 NOT_FOUND`，不泄漏组织内成员信息。
- 未登录或会话失效：返回 `401 UNAUTHORIZED`，不返回任何组织数据（见 002）。
- 撤销已使用 / 已撤销邀请：返回 `404 NOT_FOUND`，状态不变。

# 架构精简（Architecture Slimming）

> 本文件只描述可验证的行为与验收契约，不包含 SQL、框架、内部类名等技术实现细节。关键规则未澄清前不得自行猜测补全。

## 1. Overview

本变更对已批准并执行的架构精简做规范同步。目标是在**对外行为不变**的前提下，移除生产路径零引用的实现与重复定义，让同一事实只有一处权威，并把类型检查变成合并门禁。

- **范围**：纯删除与重复收敛（阶段 0、阶段 1），以及类型错误修复后的门禁落地（阶段 1.5）。
- **非目标（Out of Scope）**：不新增功能、不改变 HTTP 可见结果、不改动数据库约束与迁移、不引入依赖或依赖注入容器、不重写导出契约工具。

## 2. User Stories

- **US-01**：作为维护者，我希望删掉不承载行为的代码，以便每次改动只需要理解真正会执行的实现。
- **US-02**：作为评审者，我希望同一事实只有一个权威位置，以便不必核对多份互相抄写的定义。
- **US-03**：作为评审者，我希望类型检查在合并前自动通过，以便错误不在运行期才暴露。

## 3. Functional Requirements

> 每条需求用唯一 ID 描述可验证的系统行为。

### FR-001：移除零引用实现并带来可测量瘦身
- 生产路径中零引用的实现及其专属测试必须移除。
- 相对精简前基线，源码总量必须可测量地下降（删除行数必须大于新增行数）。

### FR-002：同一事实只有一处权威
- 路由助手、错误映射、时间戳格式、分页规则、成员角色取值、账号错误含义、测试夹具与环境加载，每类都只能有一个权威定义。
- 其他位置只允许引用该定义；不得保留等价副本或只做转出的空壳。

### FR-003：HTTP 行为不变
- 合法请求的成功结果、状态码、响应字段名与错误码文案必须与精简前一致。
- 认证、组织、项目、人物与邀请的既有合法路径不得因本次精简而改变可见结果。

### FR-004：类型检查零错误
- `tsc --noEmit` 必须输出零错误。

### FR-005：类型检查成为门禁且检查不重复
- 类型检查必须作为合并门禁自动执行。
- 同一项检查在 CI 中不得重复执行多次。

### FR-006：数据层不变量不变
- RLS 策略、触发器、迁移与数据库约束必须保持精简前状态。
- 原本会被数据存储拒绝的非法组合，精简后仍被拒绝，且错误含义不变。

### FR-007：明确不做项保持不做
- 被明确排除的工作不得出现在本次变更中：DI 版撤销会话进入生产、`withProjectRole`、导出契约工具重写、契约新鲜度 CI、进程内限流改动、`AppType` 改动、依赖或 DI 容器引入。

### FR-008：决策与规格可追溯
- 本次精简必须有决策记录、功能规格、实施计划与任务清单，并同步现行规范文档。
- 必须明确记录被放弃的两条 DI 版不变式及其放弃理由。

## 4. Business Rules

- 简单胜过聪明：没有行为回报的抽象、别名与重复定义必须删除。
- 行为不变是硬约束；任何可见结果差异都视为本次变更的缺陷。
- 同一事实只有一处权威；转出壳与手工副本不构成权威。
- 数据库层不参与本次精简。

## 5. Exception Handling

- 若发现某个待删实现仍被生产路径引用：暂停并保留该实现，不得以「计划要删」为由删除。
- 若发现可见结果与原行为不一致：回滚该收敛，先恢复行为再重新评估。
- 若类型检查仍有错误：不得把门禁合入，必须先修完错误。
